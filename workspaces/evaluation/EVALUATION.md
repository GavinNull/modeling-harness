# 通用数学建模 Agent 评测与泛化治理

版本：`2.5.0`（generic-agent v2.5）  
适用对象：遵循“定义—理解—创造—验证”闭环的多智能体数学建模研究系统。

## 1. 评测目标

本评测体系回答三个问题：

1. 候选版本能否在干净环境中完整、可信、可追溯地解决开放式建模任务；
2. 候选版本是否相对基线提升了可迁移能力，并且没有在未见任务或其他任务族上显著退化；
3. 这种提升是否在成本、时延和人工介入约束下稳定复现。

评测不预测竞赛名次或获奖概率。内部质量分只用于版本比较、失效定位和发布决策。

## 2. 最高优先级原则

### 2.1 禁止题目特化

真实历史任务仅是测量样本，不是优化对象。任何修改不得包含：

- 题号、题名、可反向识别题目的描述；
- 特定参数、答案、结果区间或标准解法；
- 仅对某个任务、数据集或背景生效的提示词示例或条件分支；
- 从隐藏测试中恢复出的原文、字段名、专属约束或评分器行为。

允许修改的对象仅是通用能力，例如需求覆盖、约束追踪、单位检查、数据质量、模型适配、独立复算、敏感性分析、证据追踪、复现和编排。

任何真实或合成任务、变体、提示词、数据、答案、评分、失败、评审及其全部衍生均是**评估或当前答案修订材料**，不是 Agent 本体的训练、动机或构建输入。去标识、抽象、跨任务处理或聚合不能改变此分类。

### 2.2 证据分层

- **原始审计证据**：包含具体失败位置、复现步骤和受控工件引用，只向主 Agent 与获授权评测治理人员开放。
- **任务无关研究动机**：仅限具可信来源、与任何任务和评测内容无关的独立一般研究，可形成 DTP/MAP 并交给构建者。
- **验证结果**：预注册的内容无关属性测试与契约测试只验证已许可修改；失败不能成为修改动机，也不得反向推导特化规则。
- 原始审计证据不得直接交给负责提示词、工具或流程修改的 Agent。

### 2.3 硬门槛优先于加权得分

任何硬门槛失败都不能被其他维度的高分抵消。通过硬门槛后，才使用多目标指标比较候选版本。

### 2.4 测试集不是永久真理

公开静态基准可能被模型见过，也可能存在题意不清、评分器过窄或环境不可复现等问题。每个基准任务必须经过独立质量验证，公开历史任务的分数不进入主要泛化分。

## 3. 基准三层结构

### A. 公开历史任务

用途：端到端流程、工件完整性、兼容性和长期回归。  
地位：参考指标，不进入主要泛化分。  
原因：题面、讨论、讲评或公开方案可能已进入基础模型训练语料。

### B. 私有隐藏变体

用途：验证系统是否掌握可迁移的能力结构，而非记忆题面。  
可变因素：数据、单位、噪声、缺失机制、约束组合、输出表示和资源预算。  
要求：变化后任务仍自洽，核心能力标签稳定，且不存在只有基准作者知道的隐式要求。

### C. 私有全新任务

用途：衡量面对未见背景、未见数据和未见约束组合时的泛化。  
要求：由独立领域作者创建，由另一组验证者检查题意、数据、可解性、评分准则、难度和捷径风险；构建者不得接触任务正文或逐题得分。

主要泛化分由 B、C 两层组成，默认权重分别为 `45%` 和 `55%`。A 层单独报告。

## 4. 基准治理与污染防护

1. 基准作者、基准验证者、系统构建者和最终评审者角色分离；
2. 隐藏任务正文、数据、评分器和参考工件存放在受控只读存储中；
3. 以内容哈希、访问日志、加密静态存储和最小权限维护工件；
4. 每次运行使用新建容器，不继承作者或上一次运行的缓存、会话和可写层；
5. 输入快照、容器镜像、依赖锁、提示词版本、模型版本、工具版本、随机种子和运行预算全部入账；
6. 私有基准中放置不影响语义的 canary 标识，用于发现不当复制或泄漏；
7. 限制对锁箱集的查询次数，只返回用于发布通过或拒绝、回滚和报告的聚合结论与能力标签；这些输出不得进入 DTP、MAP、研究请求、构建者反馈或 Agent 本体动机；
8. 一旦任务正文、参考答案或评分器细节进入构建上下文，该任务从锁箱集退休；
9. 迭代次数达到反馈预算上限后，使用未触碰的保留池轮换，而不是继续对同一隐藏集调参；
10. 对公共任务与私有任务的表现差距持续监控，异常大的公共优势标记为污染风险。

## 5. 单任务评测流程

1. **规范验证**：确认任务描述完整、数据自洽、评分标准不过窄、参考验证可执行；
2. **冻结运行包**：记录候选版本、系统提示词、工具清单、镜像、预算和种子；
3. **独立重复运行**：在相同输入、相同预算和独立干净容器中运行；
4. **机械检查**：文件清单、哈希、模式、代码入口、约束残差、引用完整性；
5. **专家盲评**：定义、理解、创造、验证分别按锚定量表评分；
6. **干净环境复现**：评审者只使用交付包中的说明、代码和数据复算；
7. **分歧裁决**：评审不读取作者推理，也不先读取其他评审意见；严重分歧由独立裁决者处理；
8. **证据封存**：保存原始审计记录；
9. **评测处置**：主 Agent 仅形成评估记录、发布通过或拒绝、回滚、报告，或通过 task-bound `RevisionDecision` 授权当前答案修订；不得生成研究请求、DTP、MAP、构建者反馈或 Agent 本体修改动机。

## 6. 重复运行与统计比较

默认设置：

- 公开历史任务：每个任务至少 `3` 次独立运行；
- 隐藏变体：每个实例至少 `5` 次独立运行；
- 私有全新任务：每个实例至少 `5` 次独立运行；
- 基线与候选使用配对配置：相同任务、资源上限、工具权限和种子集合；
- 同时报告中位数、均值、标准差、通过率、最差运行和按任务族分层结果；
- 版本比较采用按任务族分层的配对 bootstrap；报告质量差值及置信区间，不只报告点估计；
- 运行次数不足或任务族覆盖不足时，只能给出“证据不足”，不能宣称泛化提升。

随机性是系统属性，而不是可忽略噪声。某版本平均分较高但尾部失败显著增加时，不得发布。

## 7. 评分结构

### 7.1 硬门槛

硬门槛由 `gates.yaml` 定义，至少覆盖：

- 任务和硬约束完整追踪；
- 关键结论可追溯到数据、代码、推导、假设和原始证据；
- 关键结果可由独立评审者复算；
- 程序可在新建干净环境中按入口命令运行；
- 结果满足已声明的硬约束；
- 数据、结果和来源无伪造；
- 工件、代码、表格和报告相互一致；
- 无隐藏集泄漏、跨工作区越权或题目特化；
- 局限性和关键不确定性得到明确披露。

### 7.2 质量量表

`rubric.yaml` 使用 100 分内部量表：

- 定义：20；
- 理解：20；
- 创造：30；
- 验证：30。

每项使用 `0–4` 的锚定等级。总分 `85` 是内部候选发布门槛，不对应任何外部成绩。

### 7.3 多目标指标

通过硬门槛后，版本以向量比较：

```text
Q = 主要泛化质量
R = 稳定性与尾部风险
E = 证据与复现强度
C = 总成本
L = 端到端时延
H = 人工介入量
```

质量、稳定性和复现性优先；成本、时延和人工介入作为约束与 Pareto 指标，不允许通过牺牲硬门槛换取效率。

## 8. 独立一般研究 DTP 协议

主 Agent 对任何任务或评测缺陷只执行归档、评估或当前答案修订，不生成 Agent 本体缺陷包。DTP/MAP 仅由具可信来源且与任务无关的独立一般研究动机生成，并必须：

1. 显式证明没有使用任何真实或合成任务、评测内容或衍生物；
2. 映射到固定通用能力分类；
3. 禁止按内容、领域背景、标识符、参数、答案模式、失败位置或工具策略建立分支；
4. 绑定同一独立研究来源哈希；
5. 预注册内容无关属性测试与契约测试，并标记为 verification-only。

## 9. 修改准入

只有同时满足以下条件，主 Agent 才能签发 Agent 本体修改任务：

1. 修改动机是经独立审查的直接用户治理要求，或具可信来源且与任务无关的独立一般研究；
2. 没有使用任何真实或合成任务、变体、提示词、数据、答案、评分、失败、评审或其衍生作为动机或证明；
3. 修改映射到固定通用能力分类且不含内容特定分支；
4. 修改范围、风险面和回滚点明确；
5. 预注册内容无关属性测试与契约测试仅用于验证；
6. DTPV1/MAPV1 路径的 proposal 与 merge 均通过绑定校验，或独立 DirectUserExecutableInstructionV1 路径通过审查与绑定校验。

任何任务或评测失败都只可登记、评估或修订当前答案工件，不得直接或间接触发 Agent 本体修改。硬安全事件可以立即隔离和止血，但不自动产生长期本体修改动机。

## 10. 发布、停止与回滚

### 发布

候选版本只有在以下条件全部满足时才能发布：

- 所有硬门槛通过；
- 内部质量总分和各阶段最低分达到 `gates.yaml` 的阈值；
- 主要泛化分相对基线满足非劣要求；
- 任一任务族无超过容忍度的退化；
- 尾部失败率、成本、时延和人工介入未越界；
- 两个互不重叠的私有锁箱面板连续通过；
- 不存在未裁决的高严重度缺陷或评审分歧。

### 停止优化

满足以下任一条件时冻结当前方向并进入人工架构复核：

- 连续三轮主要泛化质量提升低于最小实际改进值，同时成本显著上升；
- 同一通用缺陷经过三次合规修改仍复发；
- 改进只出现在单一任务族，且跨领域或未见任务出现退化；
- 锁箱反馈预算耗尽；
- 新证据表明基准或评分器本身不可信。

### 回滚

以下任一事件触发立即回滚到最近的已验证版本：

- 新出现硬门槛失败；
- 发现隐藏数据泄漏、题目特化、伪造或隔离越权；
- 主要泛化分或任一任务族超过允许退化幅度；
- 干净环境复现失败；
- 资源消耗越过硬预算且无预先批准。

## 11. 评审质量控制

- 采用至少三类相互独立的证据：机械检查、独立复算、专家判断；
- 专家量表先使用标注样本校准，序数量表报告加权一致性；
- 自动评分器必须用专家标注定期校准，未达到一致性阈值时不得独立作发布决定；
- LLM 评审用于结构化初筛或成对比较，不作为唯一证据；
- 评分器、参考工件和任务规范同样接受版本控制、回归和缺陷审计；
- 严重分歧按保守原则裁决：硬门槛争议未解决即视为未通过。

## 12. 依据

本协议吸收了以下公开原则，但阈值与权重是本系统内部治理选择：

- [NIST AI RMF 1.0](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-ai-rmf-10) 与 [NIST TEVV](https://www.nist.gov/ai-test-evaluation-validation-and-verification-tevv)：强调可记录、可重复和可扩展的测试、评价、验证与确认过程。
- [OpenAI Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)：强调贴近真实分布、持续评测、全量日志、自动与人工校准结合，以及覆盖典型、边界和对抗样本。
- [OpenAI Agent workflow evaluation](https://developers.openai.com/api/docs/guides/agent-evals)：将端到端 trace 用于定位工作流失效，并在行为明确后转向可重复数据集与评测运行。
- [Introducing SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)：说明任务规范、评分标准、运行环境和多评审验证本身会显著影响测量有效性。
- [Why SWE-bench Verified no longer measures frontier coding capabilities](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)：公开静态任务会受到污染，评分器也可能过窄或过宽；私有原创任务与整体专家评分可提供更可靠信号。
- [Investigating Data Contamination in Modern Benchmarks for Large Language Models](https://arxiv.org/abs/2311.09783)：支持将公开基准污染视为实际评测威胁，并使用多种检测与替代测量。
- [Reproducibility and Replicability in Science](https://nap.nationalacademies.org/catalog/25303/reproducibility-and-replicability-in-science)：将计算可复现性定义为使用相同数据、步骤、方法、代码和分析条件获得一致结果。
